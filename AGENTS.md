# Repository Guidelines

## ## Project and Business Context

This repository contains Legatech's Next.js marketing website.

Legatech is a small digital agency based in Osijek, Croatia. The primary audience is Croatian small and medium-sized businesses, local service providers, entrepreneurs, and companies that need a stronger online presence, a better-performing website, more visibility on Google, an online store, or ongoing website support.

Legatech provides four core services:

- Website design and development
- SEO optimization
- E-commerce / web shop development
- Website maintenance

These four services represent the core service structure of the website. Do not introduce additional standalone services unless explicitly requested.

Local SEO, SEO audits, technical SEO, keyword research, analytics, performance optimization, and similar activities may be included as parts of the relevant core service, primarily SEO optimization, but they should not be presented as separate primary services by default.

The website must feel like a small, experienced, technically capable agency with a personal approach rather than a large corporate agency.

The main business goals of the website are to:

- build trust;
- clearly explain what Legatech does;
- help visitors identify the service relevant to their problem;
- demonstrate expertise;
- communicate business value rather than technical features only;
- show previous work and proof where available;
- answer common objections before the visitor contacts Legatech;
- explain the working process;
- give visitors an indication of pricing;
- generate qualified enquiries.

Customer-facing copy must always be written in Croatian.

The primary CTA across the website is:

**"Zatražite ponudu"**

Secondary CTAs may include:

- **"Pogledajte projekte"**
- **"Dogovorite besplatne konzultacije"**
- **"Saznajte više"**

Do not overuse CTAs. Each section should have a clear purpose in the conversion journey.

The main enquiry form should collect:

- name;
- email;
- company;
- required service;
- approximate budget;
- project description.

The website should use clear conversion paths, strong information hierarchy, concise copy, useful internal linking between related services, and repeated trust signals where appropriate.

## Content and UX Rules Across Pages

Every page should have one clear primary intent.

Do not create sections only to make pages longer.

Every section should serve at least one of these purposes:

- explain the service;
- identify a visitor problem;
- explain the solution;
- communicate value;
- differentiate Legatech;
- provide proof;
- reduce uncertainty;
- answer an objection;
- help visitors understand pricing;
- move the visitor toward the next logical action.

Service pages must not be copies of one another with different headings.

Each service page should have a structure and content tailored to the specific search intent and decision-making process of that service.

Use contextual internal linking between the four services.

Examples:

- Izrada web stranica → SEO optimizacija
- Izrada web stranica → Održavanje web stranica
- Izrada web stranica → Izrada web trgovina where relevant
- Izrada web trgovina → SEO optimizacija
- Izrada web trgovina → Održavanje web stranica
- SEO optimizacija → Izrada web stranica when technical or structural problems require a redesign

Do not introduce Local SEO, SEO audit, hosting, advertising, social media management, branding, graphic design, or other activities as new core services unless explicitly requested.

Related capabilities may be mentioned inside an existing service when they directly support that service.

Copy should:

- always be written in natural Croatian;
- be understandable to non-technical business owners;
- focus on benefits and outcomes before technical details;
- use concrete language;
- avoid generic agency claims;
- avoid unnecessary jargon;
- avoid exaggerated promises;
- never guarantee Google rankings;
- never fabricate clients, testimonials, reviews, case studies, statistics, awards, certifications, or results.

Use:

- short paragraphs;
- descriptive headings;
- scannable content;
- lists where useful;
- clear visual hierarchy;
- meaningful CTAs;
- strong internal linking.

Important service and location keywords may be included naturally, but copy must never feel keyword-stuffed.

The website should consistently communicate these Legatech qualities:

- personal approach;
- direct communication;
- technical competence;
- transparency;
- reliability;
- performance;
- SEO awareness;
- long-term support;
- focus on practical business results.

## Project Structure and Module Organization

Use the Next.js App Router with TypeScript. Place routes, layouts, and metadata in `src/app/`; reusable UI in `src/components/`; utilities and integrations in `src/lib/`; and static assets in `public/`. Keep unit tests beside modules or in `tests/`, and Playwright journeys in `e2e/`.

## Build, Test, and Development Commands

After scaffolding, expose these npm scripts:

- `npm run dev` — start the local development server.
- `npm run build` — create and validate the production build.
- `npm run start` — serve the production build locally.
- `npm run lint` — run ESLint checks.
- `npm run test` — run Vitest unit and component tests.
- `npm run test:e2e` — run Playwright browser tests.

## Coding Style and Experience Standards

Use two-space indentation, PascalCase components, camelCase variables and functions, and kebab-case routes and assets. Prefer Server Components; add `"use client"` only for browser state or interaction. Use semantic HTML, accessible labels and focus states, optimized images, and minimal client JavaScript. The design should feel modern, confident, creative, and personal, with clear hierarchy and responsive behavior.

## Testing Guidelines

Use Vitest and Testing Library for logic, validation, and interactive components. Use Playwright for navigation, responsive layouts, keyboard access, CTAs, and the complete enquiry path. Add regression coverage with every bug fix; do not assume a coverage threshold until tooling defines one.

## Commits, Pull Requests, and Security

Use Conventional Commits, such as `feat: add services section`. Pull requests require a summary, verification steps, linked issues when relevant, and screenshots for visual changes. Never commit secrets or `.env.local`. Validate enquiries on the server, use environment variables for credentials, and review new dependencies.
